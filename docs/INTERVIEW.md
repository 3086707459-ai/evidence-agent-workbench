# 求职展示与面试讲解

## 项目定位

把项目描述为“面向技术资料审阅的可恢复研究 Agent”。重点讲清楚模型做什么、确定性代码保证什么、哪些质量还需要人工评价。适合展示 Python 后端、Agent/RAG 工程，以及与嵌入式 Linux 业务结合的能力。

可以使用这段项目介绍，理解代码并亲自复现后再写入简历：

> 构建面向设备选型的证据研究 Agent，接入 OpenAI Responses 原生工具调用，支持规划、词法检索、原文引用校验和受限计算；以 SQLite 检查点、worker fencing、动作摘要审批与事务 outbox 实现可恢复执行和本地幂等工单；提供 FastAPI/SSE 工作台、无模型回放和故障恢复测试。

不要把 demo 的通过率写成 LLM 准确率，也不要在未运行真实业务时写“生产落地”“高并发”“企业级可靠性”等未经验证的经历。根据自己的实际修改和理解描述贡献。

## 五分钟演示

1. 打开工作台，说明 demo 是确定性 fixture，真实 provider 在 `providers.py`。
2. 创建 Atlas/Boreal 比较任务，展示计划、逐步轨迹、原文证据和 Decimal 计算。
3. 停在审批，说明批准绑定的是具体 payload，不是泛泛的“允许执行”。
4. 批准并展示唯一工单；重复审批请求说明幂等，旧版本说明冲突检测。
5. 点击无模型回放，展示同一报告和无额外工单。
6. 执行 SIGKILL 恢复测试，解释 prepared decision、lease 与 epoch。
7. 展示测试与评测，说明真实模型质量和部署仍待验收的范围。

## 能讲透的技术问题

| 面试问题 | 应解释的核心 |
| --- | --- |
| 为什么这是 Agent？ | OpenAI 模式每轮根据目标与工具反馈选择后续操作；demo 只是工程 fixture |
| 为什么不用多个角色？ | 任务当前规模可由一个受限循环完成；分角色增加延迟和调试成本，需实验再决定 |
| 如何保证引用可靠？ | 冻结快照、先读再引、原文子串、哈希及来源数；语义支持仍需单独评分 |
| 为什么会重复请求？ | 客户端超时不知道服务端是否已成功；幂等 key + 请求摘要解决重复创建与内容漂移 |
| 进程在哪个窗口被杀最危险？ | 模型调用与本地落盘之间可能重复计费；pending 落盘之后可无模型恢复 |
| lease 与 epoch 各解决什么？ | lease 允许超时接管；epoch 防止旧 worker 回来覆盖新 worker |
| exactly-once 到什么范围？ | 同一 SQLite 事务中的 outbox 和本地 ticket；远端服务需幂等与对账 |
| 预算是不是硬费用上限？ | 不是，usage 在返回后观测，重试/在途调用可能增加费用 |
| 事件哈希链能防管理员吗？ | 不能，管理员可重算；独立信任需外部签名/锚点 |
| 如何应对提示注入？ | 资料标记不可信，能力白名单阻止危险执行；还需评测语义偏转与报告污染 |
| 为什么选 SQLite？ | 单机演示低依赖、事务清晰；扩展前需测尾延迟和锁竞争，不能冒充分布式系统 |

可以让本 Agent 审阅 edge-linux-gateway 的配置、部署说明和测试输出，整理带证据的验收清单。当前没有自动连接该仓库、SSH、硬件操作或服务重启工具。若扩展设备操作，应保持只读诊断优先，并为每类动作设计明确边界、授权与恢复，不让模型直接控制关键设备。
